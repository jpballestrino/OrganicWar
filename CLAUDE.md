# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

OrganicWar.io is a real-time multiplayer territory-conquest browser game (Risk/Territorial.io style). A Rust simulation compiled to WebAssembly runs the cell-grid war on a 1920×1080 map (2560×1440 for Mega Battles). The **server is authoritative**: it runs the WASM sim per room and streams owner deltas to clients, which keep a plain copy of the map (one u16 per cell, same bit layout) purely as a render cache — the browser loads no WASM.

```bash
npm start      # Express + Socket.IO game server on :3000 (also runs DB migrations)
npm run dev    # Vite dev server on :5173, proxies /socket.io → :3000
```

Open the Vite URL (`:5173`) during development — it hot-reloads the client and proxies websockets to the running game server.

Exactly **one** instance: rooms live in process memory. `capacity.js` reads the container's cgroup CPU/memory limits, so room capacity follows the plan.

## Critical: rebuild the WASM after any Rust change

`server/wasm/` and `server/wasm-mega/` hold generated `wasm-bindgen` output. They are **git-ignored** (wasm-pack writes a `.gitignore` into each output dir), so they are *not* committed — the deploy regenerates them via `npm run build` (see `render.yaml`). Locally, after editing `simulation-core/src/lib.rs` you MUST run `npm run build:wasm` to regenerate *both* builds, or rooms will run stale simulation logic: a room's worker loads `server/wasm/` (standard map) or `server/wasm-mega/` (Mega map) when it starts, and checks the build's `map_width()`/`map_height()` against `MAP_SIZES`. `cargo test --release` and `cargo test --release --features mega` test both. (A leftover `src/wasm/` from older builds is unused.)

## Architecture

### Simulation core (`simulation-core/src/lib.rs`)
- `SimulationState` uses a **Structure-of-Arrays** layout (parallel `Vec`s indexed by cell id `row*1920+col`, or by player id 1–20; index 0 = neutral/unowned). This avoids per-cell objects and GC pressure.
- The hot per-cell fields are **bit-packed into one `u16` per cell** (`cell_data`): owner (bits 0–6, 0–127), terrain (7–10), defense tier (11–14), has-building (15). The bit layout is mirrored in `src/js/constants.js` (`CELL_*`), the renderer's GLSL unpack, and `src/js/mapGen.js` — change all four together. Private `cell_owner()/cell_terrain()/...` accessors do the masking in Rust.
- The cell grid is **8-connected** (Moore neighborhood): neighbours come from `NEIGHBOR_OFFSETS` (0–3 cardinal, 4–7 diagonal). `process_war_fronts` expands **radially**: each tick it scores the conquerable border shell and conquers cells (xorshift random tiebreak via `next_rand`), capped at `MAX_CONQUERS_PER_TICK` **per front**. A click (`execute_expansion`) only commits troops to a front and does **not** steer direction.
- **Multiple attack fronts**: fronts are per-target, stored as `front_pool[attacker × PLAYER_ARRAY_SIZE + target]` (target 0 = neutral land, 1–20 = a specific enemy). A faction can hold several active fronts at once (neutral + multiple enemies); `process_war_fronts` gathers candidates and resolves each front independently, spending only that front's committed troops. `player_attack_pool[f]` is kept as the per-player **sum** of all fronts (recomputed each tick) so the HUD/wire format need no per-front fields. Counter-attack annihilation cancels two mutually-aimed fronts (a→b and b→a) 1-for-1, destroying those troops. `cancel_expansion` (Space) refunds and closes **all** of a faction's fronts.
- **Border-block index** (performance): the per-tick scans in `process_war_fronts` and `bot_think_all` only care about border cells, so the map is split into 8×8 blocks (`BLOCK_SHIFT`) and a block whose cells *and* 1-cell ring all share one owner is skipped whole. `set_cell_owner` — the single choke point for ownership changes — invalidates the blocks around a changed cell (`invalidate_blocks_around`) and `block_is_active` re-classifies lazily; `is_enclosed_by_owner` rejects interior cells of border blocks with 8 compares. **Always change owners through `set_cell_owner`**, or the index goes stale and fronts stop seeing borders. Candidate lists are sorted + deduped, so the outcome is bit-identical to a full scan (a 20-bot match went 11.9 → ~1.1 ms/tick; `bot_match_report` prints the cost).
- Per-cell memory is just `cell_data` (u16), the block states and two 1-bit-per-cell sets (`fresh_cells`, `tier_changed`, 260 KB each) — ~5 MB per room; the old per-cell `troops` / `last_modified_tick` / `difficulty_to_invade` buffers are gone and `delta_scratch` grows on demand. Of the 16 bits per cell about 11 are needed (owner 7, terrain 2 of 4, defense 1 of 4 — tiers are only 0/10 — building 1); the spare bits are kept as headroom, not packed tighter (a `u16` is the smallest word that fits, and the layout is mirrored in four places).
- JS reads sim data **zero-copy** via `get_*_ptr()` exports that return raw pointers into WASM linear memory; the JS side builds typed-array views over `wasmModule.memory.buffer` at those offsets. A pointer can move when its Vec grows (`delta_scratch`, `stats_buf`), so read it **after** the call that fills the buffer.
- `tick()` advances production, war fronts, missiles, construction, Flak recharge and (when dirty) synergy links. `collect_dirty_cells()` packs every cell whose owner changed since the last call into `delta_scratch` as wire-ready u32s (`cell_id | owner << 25`); `write_stats`, `write_full_owners` and `write_buildings` produce the other exports (see **Wire format**).
- **Economy is tick-rate-aware** (`set_tick_hz`): per-second rates (troop growth, gold income) are divided by the tick rate, so the *economy* is identical at any `SIM_TICK_HZ`. ⚠️ Expansion speed is **not** normalized — `MAX_CONQUERS_PER_TICK`/`MIN_CONQUERS_PER_TICK`/`EXPANSION_CELLS_PER_TROOP` are per-*tick*, so changing `SIM_TICK_HZ` changes conquest speed unless those are scaled to match. Troop growth/sec is a downward parabola in population fill `p = troops/max_cap` (peak at `GROWTH_PEAK_RATIO`=0.40, zero at full pop, positive floor at `p`=0). Max pop cap = `owned_cells * POP_CAP_PER_CELL` (no flat base). The spawn nucleus radius, `MAX_CONQUERS_PER_TICK`, and the growth constants are all `const`s near the top of `lib.rs`. `apply_production` records each player's actual income/s, growth/s (0 at the cap) and effective cap (with city bonuses) in `player_income_per_sec` / `player_growth_per_sec` / `player_effective_cap`; the HUD shows those via `sim-stats`, so **no economy formula is mirrored in JS** (only `GROWTH_PEAK_RATIO`, to colour the growth number).
- **Anti-snowball production throttle** (`apply_production` / `oversize_growth_scale`): to stop a runaway empire out-*producing* what it loses, troops/sec is throttled above a per-match **soft cap** = `GROWTH_FAIR_SHARE_MULT` × a player's fair share of the land (`land_cells / num_players`, counted once in `init_players` since terrain is generated before it). Territory beyond the soft cap contributes only `GROWTH_OVERSIZE_FACTOR` toward production, so a giant empire's troops/sec flattens toward a mid-size one's. **Capacity/density stay linear** (`max_cap = cells × POP_CAP_PER_CELL`) on purpose: the combat model depends on it. (The client no longer derives cell counts from max pop — `sim-stats` carries cells directly.) To *also* make big empires defensively softer, diminish `max_cap` itself. The throttle bites super-linearly (the parabola pushes a lower effective fill past its peak), so tune `GROWTH_OVERSIZE_FACTOR`/`GROWTH_FAIR_SHARE_MULT` gently. Server-only (`lib.rs`); no client mirror needed since the diminished growth flows through `sim-stats`.
- **Gold economy**: `player_gold` (an `f32`, accrued each tick) grows by `owned_cells * GOLD_PER_CELL_PER_SEC` per second, plus +10% per completed gold mine (+15% for a Workforce-linked one). Gold, income/s and the live prices travel in `sim-stats`. The client renders them in the **bottom HUD bar** (`.game-hud-bottom`): Gold, Income, and the **build bar** (see **Build bar** under Client).
- **Leaderboard and Kills**: `player_kill_count` and `player_gold_spent` are tracked in the Rust simulation. Kills are awarded when an enemy cell is conquered (defending troops are added to the attacker's kill count) or when an enemy is hit by a missile blast. The client computes a score (`gold spent + kills + troops incl. those on attack + cells`) from `sim-stats` and shows the **top 10 plus the player's own row** in `gameLeaderboard`.
- Constants here (`MAP_WIDTH`/`MAP_HEIGHT` — 1920×1080, or 2560×1440 with the `mega` cargo feature — and `MAX_PLAYERS=64`) are mirrored in JS (`src/js/constants.js`: `MAP_SIZES`, `COLS`/`ROWS` = the standard size, `MAX_FACTIONS`). **Map size per room**: `mapSizeFor(maxPlayers)` — rooms of `MEGA_MAP_MIN_PLAYERS` (33)+ players play on the Mega map (64 empires on the standard map were crowded: spawns ~75 cells apart, free land gone in ~20 s). The room carries `mapSize`/`mapWidth`/`mapHeight` (sent in `init-config` and `spawn-selection-start`; the client reallocates its map with `simBridge.setMapSize` and `renderer.resizeMap`), the safe-zone radius scales with the width, and XP's land figures scale with the map's cells (`progression.landScale`). Cell ids take 25 bits on the wire. `MAX_PLAYERS` is read at runtime through the `max_players()` export and the worker **refuses to start** if it differs from `MAX_FACTIONS` (colours, shader arrays and validation are sized from it). The owner field is 7 bits, so 127 is the hard ceiling. Quick Battle uses `QUICK_PLAY_PLAYERS` (20); **Mega Battle** (`quick-play {mode:'mega'}`, the orange home-screen button) uses `MEGA_PLAY_PLAYERS` (64) — the two queues fill separate rooms (matched by `maxPlayers`), and a Mega room waits 10 s instead of 5 for humans before bots fill in. Custom rooms allow up to `MAX_FACTIONS`.

### Economy: prices, plunder, Blitz
- **Escalating prices**: `building_price(f, type)` = base × (1 + `BUILDING_PRICE_STEP` (0.25) × buildings of that type `f` already owns, finished or not, captured ones included). Used by `place_building_internal` and the bots; the six live prices (5 building types + the cheapest missile) are in every player's `sim-stats` record. The base `*_COST` consts are mirrored in `constants.js` only as the pre-stats fallback.
- **Plunder**: when a faction's last cell falls (conquest or missile blast), `plunder()` moves its whole treasury to the attacker. **Salvage**: razing an enemy defense tower by conquest pays `TOWER_SALVAGE_SHARE` (50%) of the tower's base price. Both are recorded in `plunder_buf` as `(victim, beneficiary, gold, kind)` quads and broadcast as `gold-seized {fromId, toId, gold, kind:'plunder'|'salvage'}` (kill-feed line + banner/toast in `matchFeel.js`).
- **Blitz** (key `1`, input `blitz`): `activate_blitz(f)` — for `BLITZ_SECONDS` (6) every front of `f` conquers up to `BLITZ_SPEED_MULT` (2)× as many cells per tick and pays `BLITZ_COST_MULT` (0.6)× for enemy-held cells; then `BLITZ_COOLDOWN_SECONDS` (45). `player_blitz_until` / `player_blitz_ready` hold the ticks; seconds left / cooldown left are in `sim-stats`. The worker broadcasts `blitz-started {factionId}`. Bots Blitz whenever they hold an enemy front and it's ready (never during the truce).
- **Bounty on the leader** (`update_bounty`, every tick): the largest empire gets a bounty when it holds more than the production soft cap (2× its fair share) **and** ≥ `BOUNTY_LEAD_RATIO` (1.5)× the runner-up's land. With hysteresis: an existing bounty stays on the same leader until its lead falls below `BOUNTY_KEEP_RATIO` (1.2)× or it drops under 85% of the soft cap, so it doesn't flicker. Every other faction's front against the bounty target pays `BOUNTY_COST_MULT` (0.75)× the troops per cell and earns `BOUNTY_GOLD_PER_CELL` (0.5) gold per cell taken (`player_bounty_earned`). Bots that border the target attack it ahead of anything else (outside the truce) — the counterweight only works if the runaway's neighbours gang up — and treat it as 25% weaker when comparing enemies. `matchFeel` announces the same target at most once every 30 s (bounties can lapse and return quickly once rivals pile in). `bounty_faction` is in the `sim-stats` header; the client tags the target's map label (🎯 BOUNTY) and leaderboard row, and `matchFeel` announces new bounties and toasts your bounty gold. It is the counterweight to plunder: over three 64-player runs the runner-up finished with 36–40% of the land (was 6–8% without the bounty), matches ending by domination at 4:13–4:44. Covered by `bounty_on_a_runaway_leader`.
- Measured: the native 20-bot match ends at ~410–420 s (was 580 s before these changes); 20- and 64-player worker matches end by domination at ~3.5–4 min.

### Per-cell difficulty and territory opacity
- `difficulty_to_invade(cell)` — computed **on demand** (only for cells a front is about to take), no longer stored per cell: `difficulty = floor(min((player_density + terrain_cost) × defense_tier, DIFFICULTY_CAP = 50))`. `player_density` = troops / owned_cells of the cell's owner, **sampled once a second** by `update_cell_difficulties()` into `density_snapshot` (0 for neutral). Terrain costs: plains=1, highlands=3, mountains=6, forest=4, river=5, gold=1, ruins=6. Default `defense_tier` = 1; buildings raise it to 10. Exactly the old once-a-second re-pricing of every cell (a 2 MB array rewritten for all 2 M cells each second): a cell taken since the sample costs 0 (`fresh_cells` bit, set on conquest; all set before the first sample), and a cell whose tier changed since the sample (`set_cell_defense` — a tower finished or destroyed) is priced with its tier at the sample (`tier_changed` bit + `tier_at_sample` map). Verified: the 20-bot `bot_match_report` timeline is identical to the stored-array version, at 0.82 vs 0.95 ms/tick. Any new code that changes a tier must go through `set_cell_defense`.
- **Attacker cost vs defender loss** (in `process_war_fronts`): `difficulty_to_invade` is what the **attacker** pays to take an *owned* cell. Two carve-outs: (1) conquering **neutral** land costs a flat `NEUTRAL_INVADE_COST` (=0.2) regardless of terrain — `difficulty_to_invade` only governs owned/defended cells; (2) the **defender** loses only their live troops-per-cell density (`troops / owned_cells`) when a cell falls, *not* the tiered/capped difficulty. So defense tier makes a cell costly for the attacker but never inflates the defender's loss, and an evenly-garrisoned empire reaches 0 troops exactly when it reaches 0 cells (never before).
- **Focused attack**: clicking an enemy opens a front against that faction only (`front_pool[f × PLAYER_ARRAY_SIZE + enemy]`); neutral land and third parties are excluded from that front's candidates, so its troops concentrate on the targeted player's border. Clicking own/neutral land feeds the neutral front (target 0).
- **Territory heatmap**: the GLSL fragment shader tints each owned cell with its faction colour at opacity `0.18 + 0.64 × clamp((density/25 + terrainCost/25) × defTier, 0, 1)` over the baked terrain (see **Client**). Opacity reaches 100% at difficulty=25 and is capped visually there, even though combat cost continues up to 50. The per-faction density ratio (`troops/cell ÷ 25`, from `sim-stats`) is uploaded as the `u_player_opacity[MAX_FACTIONS+1]` uniform; terrain and defense tier are read directly from the local `cell_data` texture in the shader. Shader arrays and owner bounds are sized from `MAX_FACTIONS` via the template string.

### Defense buildings
- Placed with the `'3'` key then a click. The server runs `place_defense_building(faction_id, center_row, center_col)` which **verifies the faction can afford `DEFENSE_BUILDING_COST` gold (currently 2000)**, validates the entire 8×8 footprint is owned by the faction and clear of existing buildings, stamps `BUILDING_MASK` (bit 15) on all 64 footprint cells, charges the gold, and registers the building with a **completion tick** `DEFENSE_BUILD_SECONDS` (=5s) in the future. Gold is charged only on full success (a failed validation costs nothing). `BUILDING_RADIUS`, `DEFENSE_BUILDING_COST`, and `DEFENSE_BUILD_SECONDS`/`DEFENSE_BUILD_MS` live in `lib.rs` and are mirrored in `src/js/constants.js` (the cost drives the HUD label and a client-side pre-check; the radius and build time are echoed in the `building-placed` event) — change each in lockstep.
- **Build time (gated bonus)**: placement does **not** stamp `defense_tier` — the tower is *under construction*. It occupies its footprint (blocks re-builds, can be conquered) but grants **no** defense bonus yet: `cell_in_own_building_radius` skips buildings whose `defense_build_complete[i] > current_tick`, and `update_cell_difficulties` therefore sees the default tier. `process_construction()` (called in `tick()` **after** `process_war_fronts`, so a building conquered on its completion tick is destroyed first and can't double-emit) stamps `defense_tier=10` across the radius on the builder's own cells once the time elapses, sets the building active (`defense_build_complete=0`), and pushes `(center, faction)` to `completed_buildings_buf`. The build time is tick-rate-aware (`5s × tick_hz`). Neutral and enemy cells in the radius are never affected.
- On placement the server emits `building-placed` (carrying `buildMs`) to all room clients → the client shows the tower (dimmed) with a fill bar but does **not** stamp the tier yet. On completion the server polls `completed_buildings_buf` via `_emitCompletedBuildings()` and emits `building-completed` → the client clears the `constructing` flag and stamps the fortification tier. On a failed placement it emits `build-rejected` only to the requester.
- **Bots build too**: `bot_build_all()` runs on a ~3s cadence (`botBuildEveryTicks`); each bot holding ≥300 cells that can afford a tower or a city (at **its own escalating prices**) attempts a placement — half the time near its territory centroid (jitter scales with territory size), half the time within `LINK_RADIUS − 10` of one of its completed buildings, so bots form synergy links. Each attempt rolls a type: 15% silo (only if affordable and an enemy cell is within `SILO_RANGE`), 15% anti-air, 15% gold mine, 15% city, otherwise a defense tower. A bot is capped at one building per 4,000 cells (min 1), counted by `building_owner`. Bot placements are broadcast via a `placed_buildings_buf` (mirroring the destroyed buffer) polled each tick by `_emitPlacedBuildings()`; human placements still emit `building-placed` directly from `handleInput`, so only bot builds use the buffer.
- **Bots fire missiles**: `bot_fire_missiles()` runs every 2s (`tick % (this.tickHz * 2) === 0`); bots iterate over their completed silos, preferentially targeting any enemy building within `SILO_RANGE`. If no building is in range, they sample random coordinates and blast the first enemy cell found. Bot missile fires push to `fired_missiles_buf` just like human fires, unifying the `missile-fired` broadcast.
- **Destruction**: when any enemy conquers a footprint cell, `destroy_building()` clears `BUILDING_MASK` on the footprint and resets `defense_tier=0` across the radius zone. This also **cancels construction for free** if the tower was still being built (no `building-completed` is ever sent for it). The server emits `building-destroyed` to all clients.
- **Client sync**: `applyDefenseBuilding()` / `removeDefenseBuilding()` in `src/js/simBridge.js` write the defense tier bits and building flag directly into the client's local `cell_data` copy. Defense tier bits are **never** sent via the snapshot wire format (owner bits only) — they travel exclusively through `building-completed` / `building-destroyed` events. After each `sim-delta`, `resyncZonesForCells()` re-derives the tier of just the cells that changed owner (newly-conquered cells inside a fort radius gain/lose tier 10); the full `resyncBuildingZones()` runs on a tower's destruction and a full sync. Both **skip `constructing` buildings**, since their zone isn't stamped until completion.
- **All building types share one list** via **seven** index-aligned parallel vecs (the **INVARIANT**: equal length, mutated only in `place_building_internal`/push and `destroy_building`/`swap_remove` — desync = out-of-bounds panic that kills the room; the seventh is `building_links: Vec<u8>`, the LINK_* bits — see **Building synergies**): `defense_buildings: Vec<u32>` (centers, encoded `row × MAP_WIDTH + col`), `defense_build_complete: Vec<u32>` (completion tick; 0 = active), `building_type: Vec<u8>` (`BTYPE_DEFENSE=0` / `BTYPE_SILO=1` / `BTYPE_MINE=2` / `BTYPE_ANTIAIR=3` / `BTYPE_CITY=4`), `building_charges: Vec<u8>` (anti-air interceptions left), `building_cooldown: Vec<u32>` (tick at which a silo may fire again), and `building_owner: Vec<u32>` (owning faction — read by `cell_in_own_building_radius`, `process_construction`, and `fire_missile` **instead of** `cell_owner(center)`, because a silo can outlive partial conquest while its center cell already belongs to the attacker). `place_defense_building`, `place_silo`, `place_mine`, `place_antiair` and `place_city` all delegate to `place_building_internal(...)`. `destroyed_buildings_buf` / `completed_buildings_buf` (the latter **`(center, faction, type)` triplets** — count ÷3) / `transferred_buildings_buf` (`(center, new_owner)` pairs) / `building_update_buf` (`(center, links, charges)` triplets) / `plunder_buf` feed the destroyed/completed/owner-changed/`building-updated`/`gold-seized` broadcasts via their `get_*_count`/`get_*_ptr`/`clear_*` exports; `placed_buildings_buf` does the same for **bot** placements. In the worker, building types are one table (`BUILDING_TYPES`, indexed by BTYPE) and build inputs another (`BUILD_INPUTS`), so payloads and `buildMs` are not repeated per type.
- Icons are drawn **by the GPU** (`renderer.drawBuildings` → `src/js/buildingLayer.js`): each distinct icon (type × faction × constructing × anti-air charged × low-graphics, at a small or large size) is painted once with Canvas 2D paths (`src/js/buildingArt.js` `paintBuildingArt` — the art itself) into a 2048² sprite atlas (least-recently-used slots, mipmapped), and every frame all visible icons go out in **one instanced draw** (a few floats each: position, size × pulse, rotation, atlas rect), with the spinning parts (gold-mine ring, anti-air reticle) as a second rotated sprite layer. Defense-zone rings and synergy links (dashed rings/lines with a glow) are instanced distance-field strokes (`drawShapes`). Only the per-building extras that change — construction bar, silo cooldown, anti-air charge dots — stay on the 2D overlay canvas (`drawBuildingExtras`). Building icons are therefore under the labels and other overlays. `drawBuildingPlacementPreview()` / `drawSiloPlacementPreview()` show the 8×8 footprint + zone/range while hovering in the matching build mode.

### Missile silos & missiles
- **Silo** (`'4'` key → click): `place_silo` shares the construction mechanic but costs `SILO_BUILDING_COST` (10000), builds for `SILO_BUILD_SECONDS` (10s), and grants **no** fortification — `cell_in_own_building_radius` and `process_construction`'s tier-stamp are gated to `BTYPE_DEFENSE`, so a silo's only effect is enabling missiles. The `building-placed`/`building-completed` payloads carry `type:'silo'` and `range` (=`SILO_RANGE`, 240); the client renders a rocket icon and skips defense-zone stamping. `resyncBuildingZones()` skips `type==='silo'` (and any `constructing`) buildings — the client mirror of the server's defense-only fortification.
- **Silo conquest = transfer, not destroy**: unlike a defense tower (destroyed the instant any footprint cell falls), a silo *survives* partial conquest. In `process_war_fronts` a conquered silo-footprint cell is **not** destroyed; after the cell flips, `try_transfer_silo` checks whether one faction now owns **all 64** footprint cells and, if so, sets `building_owner` to that faction and pushes to `transferred_buildings_buf`. The server emits `building-owner-changed {row,col,factionId}`; the client recolors the icon and updates who may fire it. Until the full footprint is taken the silo stays the builder's (they can keep firing even if the center cell was taken). A silo caught in a **missile blast** is still destroyed outright (the blast path destroys any building type) — only the conquest path transfers.
- **Missile** (`'2'` key → click target): `fire_missile(faction, row, col)` returns a status (`0` fired / `1` reject-with-message / `2` reject-silently). The **target cell must be an enemy cell** — never the firer's own land, never nature → status `2`, **no message** (the client pre-checks via `getCellOwner` and silently ignores such clicks, staying in targeting mode; the server re-validates and the worker emits nothing for status 2). Then it picks the **cheapest ready** completed silo of `f` that reaches the target (range `silo_range(i)`: `SILO_RANGE`, ×1.25 with Radar Guidance; price `silo_missile_price(i)`: `MISSILE_COST`, ×0.75 with Arms Industry) and requires affording that price (no silo / can't afford → status `1`, toast). On fire it charges the gold and razes every cell within `MISSILE_BLAST_RADIUS` (15): each **owned** cell loses live troop density (same model as conquest) — including the firer's **own** collateral cells in the blast — any building hit is `destroy_building`'d, and the cell becomes **0 (nature)**; nature cells in the blast are a no-op. Owner→nature rides the normal owner-delta snapshot, destroyed buildings ride `destroyed_buildings_buf`; the only extra broadcast is `missile-fired {sourceRow, sourceCol, targetRow, targetCol, factionId}` (pushed to `fired_missiles_buf` as 5 items per missile). The client calculates a proportional flight time and draws a faction-colored parabolic arc (`state.activeMissiles` → `renderer.drawMissiles`), and only triggers the blast animation (`state.activeExplosions` → `renderer.drawExplosions`) once the missile lands. Each silo has a **2s cooldown** after firing (`building_cooldown`), on top of the gold cost. A missile is **not instant**: `fire_missile` queues it in `inflight_missiles` (7 u32s per missile) with a flight time of distance ÷ 40 cells/sec, and `process_inflight_missiles` detonates it on arrival (`detonate_missile`) — the client uses the same 40 cells/sec to time its arc. Pressing `'2'` shows dashed `SILO_RANGE` rings around the player's completed silos plus a blast preview at the cursor (`drawMissileTargeting`). All `SILO_*`/`MISSILE_*` consts live in `lib.rs` and are mirrored in `src/js/constants.js` and `simulationWorker.js` — change in lockstep.

### Gold mines, anti-air batteries and cities
All three use the shared construction mechanic (8×8 owned footprint, charged on success, `building-placed` → `building-completed`) and grant no fortification. Costs/build times are `const`s in `lib.rs`; base costs are mirrored in `src/js/constants.js` (`BUILD_ACTIONS`), build times in the worker's `BUILDING_TYPES` table (sent as `buildMs`).
- **Gold mine** (`'5'`, 3,000 gold, 10s): each *completed* mine adds +10% to the owner's gold income (`apply_production`; the client mirrors this for the Income HUD).
- **Anti-air battery** (`'6'`, 5,000 gold, 10s): holds `ANTIAIR_MAX_CHARGES` (3). While a missile is mid-flight (15–85% of its path) and within `ANTIAIR_RADIUS` (400) of a completed battery whose owner is the faction **being targeted**, the battery spends a charge and destroys the missile; at 0 charges the battery is destroyed. Interceptions go out as `missile-intercepted` (8 u32s each in `intercepted_missiles_buf`).
- **City** (`'7'`, 2,000 gold, 5s): each completed city raises the owner's max population by `CITY_POP_BONUS` (5%; 10% for a Walled City). The effective cap reaches the HUD through `sim-stats` (no client mirror).
- All prices above are base prices: each further building of the same type costs 25% more (see **Economy**).

### Building synergies (links)
- Two **completed** buildings of the **same owner** whose centers are within `LINK_RADIUS` (60) cells link if their types pair up in `LINK_PAIRS`; the bit is set on both, the effect applies to one:
  Walled City (city + tower → city bonus ×2), Workforce (mine + city → mine +15%), Radar Guidance (silo + anti-air → silo range ×1.25), Arms Industry (silo + mine → that silo's missiles ×0.75), Flak Battery (anti-air + tower → +1 interceptor every `FLAK_RECHARGE_SECONDS` (20), using `building_cooldown` as the recharge timer).
- `recompute_links()` rebuilds every building's bits (O(buildings²)) only when `links_dirty` is set — on completion (`process_construction`), destruction (`destroy_building`) or owner change (`try_transfer_silo`) — at the end of `tick()`. Changes go out as `building-updated {row, col, links, charges}` (also used for Flak recharges) and links are part of `sim-full`.
- Mirrored in `src/js/constants.js` as `BUILDING_LINKS` / `LINK_RADIUS` / `RADAR_RANGE_MULT` (bits must match `LINK_*`). The renderer draws a dashed line between linked icons plus a rotating ring on each linked icon (`drawBuildingLinks`, drawn **after** `drawBuildings` because tower auras hide anything underneath), the placement preview names the links a building would form (`drawLinkPreview`), silo range rings grow with Radar, and the build-bar tooltips list each type's synergies (`linkHelp`). Covered by `building_links_form_apply_and_break`.

### Player elimination and victory
- **Two ways to win**: last faction standing, or **domination** — a faction holding the current domination share of all land wins outright. The share follows the `DOMINATION` schedule in `roomManager.js` ("sudden death", to keep matches short): 65% until 3:00, then −5 points every 30s down to a 40% floor, computed from sim ticks in the worker's `_dominationShare(tick)`; if several factions qualify the largest wins. The client reads the live value from each snapshot and announces the drops (`matchFeel.js`). The worker counts land cells once after `generateTerrain` (`this.landCells`), checks the share in `_checkAlive`, ranks the survivors behind the winner by land, and posts `gameOver` with `byDomination`. Disabled for guild wars (team games) by passing `domination: null`. Every `sim-stats` header carries `landCells` and `dominationShare` so the client can show the race under the leaderboard. Reason: once bots have fortified, the last few factions can deadlock for minutes.
- **Stalled fronts close themselves**: in `process_war_fronts`, a front that conquers nothing in a tick *because every legal target costs more than its remaining pool* (typically a few dozen troops facing fortified cells) is refunded and closed. Without this the front stays open forever — stranding the troops and, since `bot_think_all` skips any bot with an active front, freezing that bot permanently; whole matches deadlocked with every bot frozen. Covered by `stalled_front_is_refunded_and_closed`.
- **Bot opening truce**: `bot_think_all` never targets another faction during the first `BOT_PEACE_SECONDS` (50s, `lib.rs` — just past the ~45s it takes to claim all neutral land; 75s left a dead half-minute); humans are not bound. Measured on the Mega map with spread spawns, free land runs out at ~25 s (20-player rooms ~29 s), and about half the field falls in the first 90 s in both — the same share, so the truce is not lengthened for Mega Battles. A "hold back unless stronger" rule was tried and deadlocks the endgame — don't re-add it. Tune bots with `cargo test --release bot_match_report -- --ignored --nocapture` (native 20-bot match on an all-plains map).
- **Spawn selection** lasts `SPAWN_SELECTION_SECONDS` (8s) and ends early (1.5s after the last pick) once every human has chosen. `select-spawn` rejects water cells via `terrainCache.isLandAt` (the exact terrain the sim uses). The safe-zone radius is per room — `safeZoneRadiusFor(maxPlayers)` (`constants.js`: 80 cells up to 20 players, shrinking with √players to 45 for 64) × map width / 1920 (60 on the Mega map) — sent to the client in `spawn-selection-start`. Unpicked spawns (bots, idle humans) are placed by `server/game/spawns.js` `placeSpawns`: **best-candidate** sampling (`SPAWN_MODE=spread`, default) — each spawn takes, of 40 random land cells, the one farthest from every spawn so far, so factions start evenly spread (64 players on the Mega map: nearest neighbour ≥ ~140 cells, median ~185); `SPAWN_MODE=random` is the old first-free-cell rule.
- The Rust sim sets `player_is_alive[fid] = 0` in `update_cell_difficulties()` whenever `player_owned_cells[fid]` drops to 0.
- `RoomSimWorker._checkAlive()` runs after each delta (~20×/sec): reads `player_is_alive` from WASM memory, diffs against the previous snapshot's alive set, emits `player-eliminated` per newly-dead faction, and posts `gameOver` the first time ≤1 faction remains or a faction reaches the domination share (guarded by `gameOverFired`). `roomManager.js` receives it as `(winnerId, stats, byDomination) => handleGameOver(...)`, which emits `game-over`, ranks the humans by sim placement for ELO, records the match and schedules room GC.
- Dead players' name labels vanish automatically because the client only builds `state.factionCentroids` for players with `cells > 0` in `sim-stats`.
- On the client, `game-over` and the player's own `player-eliminated` are handled by `matchFeel.js` (recap screen — see the next section), not `network.js`.

### Game feel & retention layer (client-only presentation)
- `src/js/matchFeel.js` listens to the same socket events as `network.js` (registered **after** `initNetwork()`, so network's handlers run first) and owns: announcer banners, under-attack / missile-inbound alerts, rank callouts, land milestones, build hints, the end-of-match recap, spectating, and Play Again. It never sends game inputs. `network.js` feeds it per-`sim-stats` (5×/s) via `onSnapshotStats({cells, gold, rank, alive, leaderFid, landCells, dominationShare, landLeaderFid, landLeaderCells, bountyFid, bountyEarned})`. It also announces your own plunder/salvage, Blitz and bounties. Land milestones scale with the room size (`landMilestones()`, ×20/players). **Play Again** rejoins the same queue: the saved `ow_auto_quick_play` value is the mode (`standard` / `mega`). New players (fewer than 3 recorded matches) get an on-screen controls strip for the first 30s.
- **A player's match ends at their own elimination**, not at `game-over`: `player-eliminated` for the local faction shows the recap immediately (Play Again / Spectate / Main Menu). `state.isSpectating` disables canvas and key inputs in `main.js`. `game-over` arriving later just re-shows the recap with the winner. The result is settled exactly once (`settle()`), so XP is never double-counted.
- **Server payloads** (JS-side bookkeeping in `simulationWorker.js`, no Rust change): `player-eliminated` carries `{factionId, killerId, placement, aliveCount, survivedSec, peakCells, kills}`; `game-over` carries `{winner, stats, durationSec}` where `stats[fid]` adds `peakCells`/`placement`/`survivedSec`. `killerId` is exact: the sim keeps `player_last_attacker[fid]` (last faction to take a cell from that player, by conquest or missile blast; own collateral excluded; exported via `get_player_last_attacker_ptr`), which at elimination is the eliminator. Covered by the `cargo test` in `lib.rs`.
- **Play Again** sets `sessionStorage.ow_auto_quick_play` to the mode then `quitAndReload()`; `initLobbyUI` consumes it (`consumeAutoQuickPlay()` returns the mode or null) and auto-emits `quick-play` for that queue.
- `src/js/progression.js` — XP, levels, rank titles, day streak and 3 daily missions; rendered into every `.progress-card` on the home screen. **One pure scoring core** (`normalizeProfile`, `scoreMatch`, `dayKey`) shared by client and server, and two homes for the profile:
  - **Guests**: `localStorage` (`ow_profile_v1`), scored in the browser (`applyMatchResult`).
  - **Logged-in players**: the server's `user_progression` table (migration 006, one JSON profile per user), scored **on the server** by `server/game/progression.js` from the worker's own match numbers — the browser never computes or uploads their XP. The server pushes `progression-profile {profile, canImport}` on connect and `progression-result {lines, totalXp, before, after, leveledUp, missions, profile}` when the player's match ends (`awardMatchXp`: at their `player-eliminated` via the runner's `onPlayerEliminated` hook, or at `handleGameOver`; exactly once per player per match via `humanPlayers[fid].xpAwarded`; never for guests or players who quit). The client switches to server mode (`setServerMode`) when logged in, shows "Loading your progress…" until the profile arrives, and the recap shows "Saving XP to your account…" until the result arrives.
  - **First login** with XP earned as a guest: the client offers its local profile once (`progression-import`); the server stores it only if the account has no profile yet and `validateImport` finds it plausible (≤ 2,000 XP per game, wins ≤ games, …) — localStorage is editable.
  - **Days** (streaks, daily missions) follow the player's own midnight: the socket handshake carries `tzOffset` (`Date#getTimezoneOffset`), validated by `parseTzOffset` and saved with the profile for scoring while the player is offline.
  - The worker supplies the per-faction inputs the browser used to count itself: `eliminations` (from `killerId`), `towers`, `missiles` and `tookLead` (#1 on the scoreboard for `LEAD_HOLD_SEC` = 3 s, same rule as the client) — in the `player-eliminated` payload and the game-over `stats`. Mission goals, XP rates, land milestones and the under-attack threshold are calibrated to measured 20-bot matches (fair share ≈63k land of ≈1.26M) — re-measure if map size or expansion pacing change. Bigger rooms are scored as their **standard-battle equivalent** (`fieldScale(players)` = players/20, min 1): land × scale, placement ÷ scale (top 16 of 64 ≈ top 5 of 20), Victory XP × scale (480 in a Mega Battle); placement, elimination and survival XP already scale on their own. Mission cards show the Mega target next to the standard one (`megaTarget`, e.g. "· top 16 in Mega Battle"). Covered by `src/js/progression.test.js` (`npm test`). In-match toasts are moved bottom-right by `body.in-match` (`feel.css`) so they don't cover the leaderboard.
- **Kill feed in big rooms** (`network.js` `addKillFeedEntry`): eliminations that don't involve you fold into one "+N more eliminated" line once three arrived within 4 s (a Mega Battle opening loses ~30 factions in a minute).
- `src/js/sfx.js` — synthesized Web Audio effects (no asset files), unlocked on first user gesture, mute persisted (`ow_sfx_muted`, toggle in the Esc menu). Styles live in `src/styles/feel.css`.

### Server (`server/`)
- `server.js` — Express + Socket.IO bootstrap, Helmet CSP (note `wasm-unsafe-eval` is required), JWT-from-handshake auth middleware that attaches `socket.userId`/`username`/`guildTag` (guests get `socket.isGuest`).
- `game/simulationRunner.js` — `RoomSim` proxy class. Wraps a Node.js `worker_threads` Worker to offload the heavy WASM simulation from the main event loop (enabling horizontal scaling across CPU cores). Accepts `onGameOver` and `onReady` callbacks. Proxies player inputs down via `postMessage`; relays the worker's `emit` (room broadcast), `emitToFaction` (e.g. `build-rejected`) and `emitToSocket` (`sim-full`) messages, and keeps the latest `load-report` in `room.simReal.load`. `sendFullState(socketId)` asks the worker for a full-state sync — called from `reconnect-to-game` **after** the socket joined the room, so no later delta is missed.
- `game/simulationWorker.js` — The dedicated background thread for a room. **One WASM instance per room**, ticking at `SIM_TICK_HZ` (default 25); calls `set_tick_hz` so per-second rates stay correct. **Generates the static terrain into the sim's packed buffer (`generateTerrain`)** and posts a `ready` event back to the main thread before spawns are placed. Instantiates the node-target WASM directly (not through the wasm-bindgen JS wrapper) to reach linear memory. `buildImports()` stubs wasm-bindgen imports dynamically because their names carry a per-build hash. Sends `sim-delta` (~20/s, skipped when nothing changed) and `sim-stats` (~5/s) as transferred ArrayBuffers, and `sim-full` on request (see **Wire format**). Every 5 s it posts a `load-report` (avg/worst tick ms, share of the tick budget used, WASM heap MB, KB/s). Input validation is against `max_players()`.
- `game/capacity.js` — how many rooms this process may run: `MAX_CONCURRENT_ROOMS` if set, else min(8 per CPU core, 80% of the memory left after ~150 MB for the server, at 64 MB/room) — CPU and memory are the **container's** cgroup limits when there are any (`SIM_CORES` overrides); a new room is also refused while the running sims use more than 75% of the cores (from their load reports). `createRoom` / ranked / guild-war creation call `roomRefusal()`; a refused player gets `matchmaking-failed` and the client returns to the menu. `/healthz` reports `capacity` plus each room's `load`.
- `ads.js` — optional **Google AdSense**, off unless `ADSENSE_CLIENT` (a `ca-pub-…` id) is set: `adsConfig()` (also served at `GET /api/client-config`), `/ads.txt`, and `cspDirectives()` which adds Google's ad domains to the Helmet CSP **only** when ads are on. Optional `ADSENSE_SLOT_HOME` / `ADSENSE_SLOT_RECAP` (display units), `ADSENSE_GAME_BREAKS=1` (Ad Placement API interstitial between matches), `ADSENSE_TEST=1`. Client side: `src/js/ads.js` — side-rail units on the home and recap screens (≥ 1150 px only), and `adBreakThen(next)`, used by the recap's Play Again / Main Menu (`leaveMatch` in `matchFeel.js`), which always calls `next` exactly once (immediately if the script is blocked, at most 40 s otherwise) and mutes sfx during the break. Never during a match. `GET /privacy` serves `server/pages/privacy.html` (contact from `CONTACT_EMAIL`, advertising section only when ads are on) — a draft the owner must review. Tests: `server/ads.test.js`, `scripts/smoke-ads.mjs` (Google's script replaced by a stand-in).
- **Accounts** (`routes/authRoutes.js`, `auth.js`, `email.js`): JWT (7 days) in `localStorage`, bcrypt; login by username **or** email; email verification and password reset by emailed one-time links (`/api/auth/verify-email`, `/reset-password` page → `POST /api/auth/reset-password`; a reset voids the account's other reset links). Verification is enforced only when email works: with SMTP off — or if the mail server refuses the message — a new account is auto-verified rather than locked out, and forgot-password answers 503 "not available" instead of pretending to send. `rateLimit.js` (in-memory, per IP and per email) caps login (30/15 min), register (10/h), reset/verification emails (5/h) and reset attempts; `AUTH_RATE_LIMITS=off` disables it. `GET /api/client-config` tells the client which social logins exist (`oauth`) so it hides the others. Covered by `server/accounts.test.js`, `scripts/e2e-accounts.mjs`, `scripts/smoke-accounts.mjs`.
- **Guilds and guild chat** (`routes/guilds.js`, `game/guildRooms.js`): a logged-in socket sits in the Socket.IO room `guild:<id>`. Membership changes come over REST while the player stays connected, so **every** route that changes it calls `joinGuildRoom` (join + chat history + online list) or `leaveGuildRoom` (leave + clear chat) on the player's socket — create, invite accepted, request accepted (`guild-update {type:'accepted', guildId}`), open join, leave, kick (`kicked`), disband (`disbanded`). The client (`guildUI.js`) reacts to those events whether or not the Guild Hall is open, refreshing the header with `renderAccountHeader()` (no socket reconnect). Chat is stored raw and rendered with `textContent` (never HTML-escape it on the server). A Guild War can only be accepted if that challenge was really sent in the last ~60 s (`pendingWarChallenges`), at the challenger's team size. One socket per account: a second login disconnects the first, and the old socket's disconnect must not drop the new one from `userSocketMap`.
- **Bad connections and quitting** (`roomManager.js` `handlePlayerDisconnect` / `reclaimSlot`, client `network.js`): a dropped player's faction **holds still** for `RECONNECT_GRACE_SECONDS` (30, env) — slot `disconnected` — then a **bot plays it** (`away`, `awaySince`) until they return: the reconnect token stays valid all match, and `reconnect-to-game` hands the faction back from the bot (`reclaimSlot`). Quitting from the menu (`quit-game`, acknowledged before the page reloads) is final: bot at once, slot `left`, tokens dropped, `humanPlayers[f].status = 'abandoned'`. Everyone is told via `player-connection {factionId, nickname, state: reconnecting|back|away|left}` (kill-feed line; leaderboard 📡 / 🤖 from the slot flags). A room whose only humans are away keeps running `AWAY_KEEP_SECONDS` (120) for them (`checkRoomGC` reschedules itself). Tokens of a finished match are remembered 10 min (`endedMatchFor`) so a returning player is told "the match ended — X won" (`reconnect-failed {reason:'ended'|'expired'}`). Reconnecting during spawn selection re-sends `spawn-selection-start` with the time left (`room.spawnTicksLeft`). Client: Socket.IO retries every 0.5–2 s; a watchdog shows the overlay when the 5/s `sim-stats` stop for 2.5 s (a stalled, not closed, connection) and forces a new connection after 7 s; `io server disconnect` (logged in elsewhere) shows an error instead of retrying forever. Server pings every 10 s with a 10 s timeout (dead connections noticed in ≤ 20 s). Covered by `scripts/smoke-network.mjs` (a TCP proxy that freezes or cuts one player's connection).
- **Ranked** (`game/ranked.js` pure logic + `roomManager.js` `matchmakeRanked` / `createRankedRoom`): logged-in players only, one queue entry per account, and a player in any room's slot can't queue or enter another match (`holdsSlotInRoom`). `planRankedMatches` groups the queue by rating — each player accepts a range that widens with waiting time (`ratingWindow`: ±100 + 10/s, any after 90 s); a group of 2–8 starts when full or when its longest waiter has waited 15 s. A ranked match is a normal 20-faction battle on a random map (bots fill the rest; room `isOpen = false`, so never in the lobby). Rating = pairwise Elo among the humans by final place (`rankedEloDeltas`, K = 40 spread over the opponents, zero-sum); players who quit rank below everyone who stayed, while leaving **after** being eliminated is not quitting (`humanPlayers[f].eliminated`, set from the worker's elimination hook). Only ranked matches change `elo_rating`. Each player gets `ranked-result {eloBefore, eloDelta, place, humans}`, shown on the recap. `init-config` carries `isRankedMatch` / `isGuildWar` (+ guild tags). Covered by `server/game/ranked.test.js`, `scripts/e2e-ranked.mjs`, `scripts/smoke-ranked.mjs`.
- **Guild wars** (`roomManager.js` `createGuildWarRoom` / `startGuildWarCountdown`, worker `teams`): two guilds, `teamSize` a side (2/3/5), by challenge (`guild-war-challenge` → `guild-war-accept`, see Guilds) or the queue (`matchmakeGuildWars`, rating gap allowed widens with waiting time like ranked). The room is private (`isOpen = false`; `join-room` admits only members of the two guilds and seats them on their own side automatically). A full roster starts at once; otherwise at `GUILD_WAR_MUSTER_SECONDS` (60) the war starts with whoever came if both sides have someone, else it is called off (no rating change). **No bots**: empty slots stay empty and a dropped/quitting player's faction idles (`botsAllowed(room)`). The sim worker gets `teams` (fid → guild id): attacks and missiles on an ally are refused (`notification` "That's your ally"), and a **team** wins — last team standing, or holding `GUILD_WAR_DOMINATION` (75% of the land together, easing from 4:00 to 50%); every member of the winning team gets placement 1. Only the **guilds'** rating changes (`guildEloDelta`, zero-sum Elo, K = 32; `guild-war-result` shown on the recap); players' own ratings never change in a guild war. `bench-room.mjs` takes `TEAMS=2`.
- **Competitive stats** (migration 007, `database.js` `getRankedPlayersPage` / `getGuildRankingsPage` / `getCompetitiveStats`, client `authUI.renderProfileModal`, `rankingsUI.js`, `ranks.js`): each `match_history` row stores `mode` (ranked / quick / mega / guild / custom), `placement` / `players` (among all factions; quitters last), `human_place` / `humans`, `elo_delta` / `elo_after`. Player rankings list only players with a ranked match: global position (also when searching, via `RANK()`), tier (`ranks.js`: Bronze < 1100 ≤ Silver < 1300 ≤ Gold < 1500 ≤ Platinum < 1800 ≤ Diamond; Unranked with no ranked match), ranked games, win rate (1st among the humans), average place, rating (peak on hover). Guild rankings: guilds with a war first (position, W–L, win rate, rating), then unrated ones. The profile shows the ranked block (tier, rating, #position of N, games, win rate, avg place, wins, peak, rating to next tier), all-mode numbers (games, victories, top-3 rate, avg place, kills, land), the last 10 finishes and the last 15 matches (mode, place/of, rating change, kills, land, duration). Covered by `server/stats.test.js`.
- `game/progression.js` — server-side XP for logged-in players (see **Game feel & retention layer**): `sendProfile`, `importGuestProfile`, `awardMatchXp`, `parseTzOffset`. Covered by `server/game/progression.test.js`.
- `game/roomManager.js` — room lifecycle, lobby list, matchmaking (ranked + guild war), spawn-selection → finalize → `startMatchNow` (which creates the `RoomSim` with the `onReady` and `onGameOver` callbacks), game-over scoring (ELO), room GC. Contains a legacy `MockSimulation` class still attached as `room.sim` for compatibility (centroids, shop costs); the real authoritative sim is `room.simReal`.
- `game/socketHandlers.js` — all `socket.on(...)` event wiring; routes `sim-input` to `room.simReal.handleInput(fid, input)`. The `build-rejected` event is now routed back directly by the proxy via an `emitToFaction` IPC message. `game/state.js` — in-memory `activeRooms`, queues, socket maps; `game/gameLoop.js` — matchmaker/player-count intervals.
- `database.js` — `better-sqlite3` (`DB_PATH`, default `server/organicwar.db`, WAL mode; `:memory:` under `NODE_ENV=test`); hourly online backups go to `backups/` next to it (`BACKUP_DIR` overrides). `migrate.js` runs numbered SQL files in `migrations/` on startup, tracked in a `migrations` table — add schema changes as new numbered files, never edit applied ones.
- `routes/` — REST for auth (`/api/auth`), guilds (`/api/guilds`), and general API.

### Client (`src/`)
- `main.js` — entry. Bootstraps all UI init functions, the home-screen cellular-automata background (drawn as one small bitmap scaled up, only when it steps), the context-aware Escape key chain (`ESC_BACK_CHAIN` — Esc in a build/targeting mode cancels **only** the mode), and `startSimulationEngine()` which loads WASM, creates a local `SimulationState` render cache, paints static terrain once, and starts the WebGL render loop. Clicks emit `select-spawn` (spawn phase), go to `buildBar.handleBuildClick` while a build/targeting mode is active, and otherwise emit `sim-input` `expand`. `Space` recalls all attacks; right-click cancels a mode (or a front). Errors show a small dismissible notice (`showErrorNotice`; details only with `?debug`, which also exposes `window.__owState` / `window.__owCountOwned` for the browser test). **Left-drag pans the camera**, so left clicks are dispatched on mouse-*up* and only if the pointer moved less than 6px; right-click (cancel a front; on own land = the neutral front) fires on mouse-down. Camera: WASD/arrows, wheel zoom, Shift+wheel adjusts attack %. The camera keys are read by **physical key** (`e.code`: KeyW/A/S/D — the same positions on AZERTY etc.) in `renderer.setupControls`, all released on window `blur` / tab hidden (a keyup missed while unfocused left a key stuck down), and the match starts zoomed in on the player's land — the picked spawn, or the server's `start-match-now` centroid when they didn't pick one (at the whole-map zoom the map fits the screen and the keys can't move it). Game keys (camera, build hotkeys, Space) are ignored only while a **visible** text field has the focus (`js/typing.js` `isTyping()`; hidden menu inputs used to keep the focus and swallow them). Covered by `scripts/smoke-camera.mjs`.
- **Build bar** — `js/buildBar.js` + the `BUILD_ACTIONS` table in `constants.js` (one row per action: hotkey, name, wire `type`, sim-input, base cost, `priceKey`, preview method, tooltip). The table drives the generated buttons (`gameUITemplate.js`, real `<button>`s in hotkey order with owned-count badges), the hotkeys `1`–`7`, click placement, affordability (live prices from `sim-stats`), the `build-rejected` messages and the placement previews. Blitz is an `instant` action with a per-frame countdown. Adding a building = one table row (+ the sim/worker side).
- `js/network.js` — Socket.IO client + all server-event handlers: `sim-delta` → `applyOwnerDelta`, `sim-stats` → `applyStats` (HUD, leaderboard, labels, shader opacity, `matchFeel`), `sim-full` → rebuild owners / buildings / stats and centre the camera; building events; `matchmaking-failed`; feed lines for plunder and enemy Blitz. `showMatchHud()` is shared by match start and reload.
- `js/simBridge.js` — owns the client's map: a plain `ArrayBuffer` of one u16 per cell (`setMapSize`, `cellView`, `mapWidth`/`mapHeight`), terrain painted by `repaintTerrain(mapId)` from a Web Worker (`terrainWorker.js`; the map shows open sea until it arrives, the standard maps are prefetched at startup by `prefetchTerrain`). It decodes the wire format into that map (`applyOwnerDelta`, `applyOwnerRuns`, `decodeStats`, `clearAllBuildingBits`); also provides `applyDefenseBuilding` and `removeDefenseBuilding` to directly write defense tier and building flag bits into `cell_data` from building events. After each delta only the cells that changed owner get their fortification tier re-derived (`resyncZonesForCells`); the full `resyncBuildingZones` runs only on rare events (a tower destroyed, a full sync). Every write marks the rows it touched for the renderer.
- `js/renderer.js` — `WebGLRenderer` keeps the packed `cell_data` in one R16UI texture and unpacks owner/terrain/defense/building in GLSL. The **terrain look** (palette per terrain code, relief shading from a height field, coast shallows and surf, river/forest/gold/ruins) is rendered **once per map** into an RGBA8 texture (`bakeTerrain`, `TERRAIN_BAKE_FS`, re-run when `simBridge.terrainVersion()` changes); the per-frame shader only samples it and tints owned cells. Faction labels are placed biggest empire first (own, then the bounty target, first) and skipped when they would overlap a placed label or the territory is under ~22 px on screen (`drawFactionLabels`) — the Mega Battle declutter. It uploads **only the 32×32-cell tiles that changed** (`simBridge.takeDirtyRects()`: runs of dirty tiles along a tile row as one rectangle, via `UNPACK_ROW_LENGTH`; the whole map when over half of it changed; every write into `cell_data` in `simBridge.js` marks its tiles), and nothing when nothing changed. It used to upload whole changed rows — fine for a player, but a spectator's changes cover the whole map, so nearly every row: 11.6 MB/s and 24 ms per frame in a Mega Battle, now 0.4 MB/s and 0.14 ms. Behind the end-of-match recap (`#matchEndOverlay`, which no longer uses `backdrop-filter`: blurring a live canvas re-blurs it every frame) the map is redrawn only 4× a second. Building links are paired only among buildings in view (O(n²)) and drawn by the GPU (see **Defense buildings**: icons). `resyncZonesForCells` looks up only the towers near each changed cell (a 64-cell grid). `renderer.stats` counts frames / uploads / bytes / ms (`scripts/bench-render.mjs`); `js/mapGen.js` generates static terrain into the packed buffer's terrain bits (used by both client and server — see **Map pool & terrain generation**); `js/state.js` — global client `state` object + `resetGameState()`. State includes `buildings: []` (list of placed building descriptors) and `activePurchaseMode` (null or `'defense_building'`).

### Map pool & terrain generation (`src/js/mapGen.js`)
- **One shared generator, run on both client and server**, so terrain is byte-identical (the whole owner-delta wire format is keyed by absolute `cell_id`, which requires both sides to agree on the map). `terrainCodes(mapId, width, height)` returns the finished map, one terrain code per cell (cached, 3 entries); `generateTerrain(memory, ptr, mapId, width, height)` / `writeTerrainBits(cells, codes)` write it into the terrain bits; `terrainAt(nx, ny, mapId)` is the pure base classifier. An **unknown `mapId` falls back to `north_america`** (a throw here would kill the worker/room). A map takes 1–2 s to compute (~2 s more at Mega size), so **nobody computes it on a hot path**: the server computes every map at boot in a background thread (`server/game/terrainWarmWorker.js` → `terrainCache.js`, SharedArrayBuffers handed to each room's worker as `opts.terrain`; a room worker that had to compute its map posts it back) — a room starts in ~0.2 s instead of 2.4 s (3.7 s Mega); the browser computes it in a Web Worker.
- **Terrain codes** (`TERRAIN`, bits 7–10): 0 plains, 1 highlands, 2 mountains, 3 water, plus four **features** `addFeatures` places deterministically (seeded from the map id and size): **4 forest** (noise blobs, ~12% of the land; neutral cost ×3, attack cost 4), **5 river** (2-cell fords from inland down the distance-to-sea field, bending along a noise flow field; neutral ×5, cost 5 — natural borders), **6 gold deposit** (blobs; +`GOLD_DEPOSIT_PER_CELL_PER_SEC` 0.1 gold/s per cell to the owner, counted per player in `set_cell_owner` as `player_gold_cells`), **7 ruins** (neutral ×10, cost 6, `RUINS_GOLD_PER_CELL` 8 gold per cell taken from neutral). Mirrored in `lib.rs` (`TERRAIN_*`, `NEUTRAL_*_MULT`), the renderer's bake and `terrainCost`, and the hover hint (`main.js` `TERRAIN_HINTS`). Covered by `terrain_features_gold_ruins_forest`; 20-bot matches still end at ~3–3.5 min.
- **Map pool**: `MAP_POOL = ['north_america', 'europe', 'africa', 'south_america', 'asia', 'oceania', 'pangaea']` (+`MAP_LABELS`, `isValidMapId`, `randomMapId(size)`); Mega Battles draw from `MEGA_MAP_POOL` (the maps with ~half or more land: not South America / Oceania, ~35%). The map id **IS the room's `preset`** (one source of truth) — decided server-side, never by the client. `north_america` and `europe` are **baked hex bitmaps** sampled with a noise-dithered lookup (`isLandNA`/`isLandEU`): `NA_MASK` (192×108); `EU_MASK` (320×180), rasterized offline from Natural Earth 50m coastline. `africa` uses a runtime-rasterized polygon mask (`AF_MASK_BITS`). `south_america`, `asia` and `oceania` are built by **`polygonMap({lon, lat, maskW, maskH, polys, ranges, plateaus})`**: [lon, lat] coastline polygons filled even-odd across all polygons (so a polygon inside land — Caspian, Baikal — is a lake) by scanline into a mask **the first time the map is used**, mountain `ranges` and high-ground `plateaus` as lon/lat ellipses. Oceania leaves out New Zealand and the Pacific islands (they would need 1,500 km causeways). `pangaea` is procedural: seeded fractal noise with an edge falloff (one supercontinent, ~52% land) and ridged-noise mountains. Land share: NA/EU 61%, Asia 59%, Africa/Pangaea 52%, South America 38%, Oceania 35%. To regenerate `EU_MASK`: fetch `ne_50m_land.geojson`, keep rings whose |area| clears a threshold (drops islets), even-odd rasterize to 320×180, hex-encode (nibble bits 3,2,1,0 → 4 cells, matching the decoder).
- **Quick Battle picks a random map** (`createRoom(…, isQuickPlay)` → `randomMapId(mapSizeFor(maxPlayers))`). The id flows to the client via `init-config.currentPreset` and `spawn-selection-start {mapId}`; the client calls `simBridge.repaintTerrain(mapId)`. The custom-lobby `mapPresetSelect` dropdown lists every map (validated against `MAP_POOL`).
- **Island bridging** (`computeBridgeCarveIndices(land)`): no land mass may be sealed off by water (an island spawn would be missile-only, near-invincible). Pass 1 erases sub-`MIN_ISLAND_SIZE` (300) noise speckles to water. Pass 2 connects each landmass to its **nearest neighbour** (not just the mainland): each round, every not-yet-connected component runs a water-only BFS to the closest land of a different union-find set and carves the gap into a `BRIDGE_HALF_WIDTH`-wide (5-cell) plains bridge, written back into the land grid so the next round sees merged components — so island **chains** (Ireland → Britain → mainland, the Indonesian islands) link with short causeways instead of one long crossing. Iterates until one component. `terrainAt` is the *pre*-bridge classifier, so the server checks spawns against the cached finished map (`terrainCache.isLandAt`), falling back to `terrainAt` only before the cache is warm.
- `js/components/*.js` — HTML-string UI templates; `js/initDOM.js` injects them. Vite root is `src/`, build output is `../dist/`.

### Fog of war and minimap
- **Each human player is sent only the map changes it can see** (lag: a 20-player match's map stream went from ~30 to ~9 KB/s per player on the wire, a Mega Battle's from ~56 to ~7 KB/s — `bench-room.mjs`). Vision is per **8×8 block**: the sim's `compute_vision()` (lib.rs) sets, per block, a u64 with bit `f − 1` for each faction that sees it — the blocks within `VISION_RADIUS_BLOCKS` (6 = 48 cells, a disk, separable dilation) of any block holding its land, plus everything within range of its **completed silos** (`silo_range`, so Radar Guidance widens it — a silo can always see what it can hit, and a player can aim missiles into land it otherwise couldn't see) — and `coarse_owner`, each block's centre-cell owner (the minimap layer). `MAX_PLAYERS` = 64 fits the u64 exactly. Covered by `vision_covers_own_land_its_surroundings_and_silo_range`.
- **Worker** (`server/game/fog.js` `FogOfWar`, wire format `src/js/fogCodec.js`): the view is recomputed ~5×/s (`visionEveryTicks`); viewers are the alive factions not played by a bot. Each tick a viewer gets (1) `sim-vision` when its view changed — blocks that came into view **with their 64 owner bytes** (it got none of their changes while fogged) and blocks that left it — then (2) its own `sim-delta` with only the cells in blocks it sees (or knew until this update). Everyone else in the room (spectators, the eliminated) gets the full delta, **batched to ~5 a second** (`specEveryTicks`, `_flushSpectatorDelta`: each cell changed since the last batch once, with its owner at send time; flushed before any whole-map `sim-full` so the two line up) — whole-map stream 28.8 → 8.8 KB/s on the wire in a 20-player match: the worker posts `emitFogged {event, perFaction: [[fid, buf]], fallback}` and `simulationRunner.js` sends each player its buffer and the rest of the room the fallback (`.except`). `sim-coarse` (the minimap layer, changed blocks in the sim-delta format with block ids) goes to everyone once a second (~1 KB/s). A player who is eliminated is sent a whole-map `sim-full` at once (spectator view; `fogged` set). Guild wars: teammates share vision (`fog.setTeams`). `sim-full` for a playing faction is fogged: `owners: null`, `vision` (everything it sees), `coarse` (whole layer); for anyone else `owners` (whole map) and `vision: null`. Fog work costs ~3 ms per second per viewer (`load-report.fogMsPerSec`).
- **Client** (`simBridge.js`): per block `vis` (255 seen / 0 fogged) and `coarse`; fog is off before the match and while spectating (`setFogOff`); the first `sim-vision` of a match fogs every block it doesn't list. Under fog the renderer draws the coarse layer dimmed over greyed terrain (`u_vis_tex`, linear-filtered for a soft edge, `u_coarse_tex`); what the cells under it hold is just the last thing seen. Rival buildings in the fog aren't drawn, and a missile can't be aimed into fog (`isCellVisible`). Building, missile, stats and leaderboard events still go to everyone (labels and the leaderboard stay global). **Minimap** (`minimap.js`, `#minimap`, bottom-left): one pixel per block — terrain, every empire from the coarse layer, fog darkened, the camera's view; click/drag moves the camera. Covered by `simBridge.test.js` (fog), `smoke-browser.mjs` (fog on, minimap, reload) and the bench.

### Wire format (server → client)
Encoded by the sim's export functions + `server/game/simulationWorker.js`, decoded in `src/js/simBridge.js` — keep them in sync. All little-endian, all binary payloads are ArrayBuffers (one websocket frame each).
- **`sim-delta`** (~20×/s, only when something changed): the sim's `collect_dirty_cells()` lists the changed cells as u32 `cell_id (25 bits) | owner << 25`, sorted by id; the worker sends them as **varint(cell_id − previous id) + u8 owner** per cell (`src/js/deltaCodec.js`, shared by the worker, the client and the bench). Measured on the same recorded 20-player match: 58% less on the wire after permessage-deflate than the old 4 bytes per cell. **permessage-deflate threshold is 256 bytes** (`server.js`): a player's fogged deltas are a few hundred bytes each, and compressed with the context kept between messages they shrink ~3× (9.1 → 2.8 KB/s per player); `bench-room.mjs` emulates it (`WIRE_THRESHOLD`).
- **`sim-stats`** (~5×/s): from `write_stats(land_cells, domination_share)`. 20-byte header: u32 tick, u32 land cells, f32 domination share, u16 player count N, u16 record size, u32 bounty faction (0 = none). Then N records of `STATS_RECORD_BYTES` (80): f32 home troops, f32 troops on attack, f32 effective max pop, u32 cells, f32 gold, f32 income/s, f32 growth/s, f32 kills, f32 gold spent, u16 centroid row, u16 centroid col, u32 flags (1 alive, 2 bot), f32 prices ×6 (defense, silo, mine, anti-air, city, cheapest missile), f32 blitz seconds left, f32 blitz cooldown left, f32 bounty gold earned. Records cover the match's players only (`num_players`), not the engine cap (a Mega Battle's stats are ~25 KB/s per client).
- **`sim-vision`**, **`sim-coarse`**: see **Fog of war and minimap**; `sim-delta` is per player under fog.
- **`sim-full`** (to one socket, on reconnect / reload; to a player when eliminated): `{ owners, vision, coarse, buildings, stats }` (fogged for a playing faction — see **Fog of war**) — `owners` is `write_full_owners()`: run-length u32s `length (24 bits) | owner << 24` covering every cell (~40–65 KB mid-match vs 4 MB raw); `buildings` from `write_buildings()` (7 u32 per building: center, owner, type, completion tick, charges, cooldown, links) turned into the same objects as `building-placed` plus `constructing`/`remainingMs`/`links`; `stats` is a `sim-stats` buffer.
The client merges only **owner bits** (bits 0–6) into its local `cell_data`; terrain is generated locally and defense-tier / building bits come from building events (cleared and re-stamped on `sim-full`). Measured per client in a 20-player match (`bench-room.mjs`): deltas ~50 KB/s raw, ~28 KB/s on the wire after permessage-deflate (was ~75 / ~66 KB/s with 4 bytes per cell), plus ~8 KB/s of stats.

## Game flow

Quick Play / custom / ranked / guild-war all converge: lobby → `startSpawnSelection` (8s, ends early once every human has picked; clients pick land spawn cells, radial safe zones radius 80) → `finalizeSpawns` (fills empty slots with bots, auto-places missing spawns on land outside safe zones) → `startMatchNow` (spins up `RoomSim` with `onGameOver` callback, spawns each faction's circular nucleus) → ticking sim streams `sim-delta` / `sim-stats` → `_checkAlive` detects eliminations and victory (last standing, or domination with a target that shrinks after 3:00) → `handleGameOver` records match + ELO and schedules room GC. Measured 20-bot matches (`scripts/bench-room.mjs`) end by domination at about 3.5 minutes; 64-player rooms at about 4.
